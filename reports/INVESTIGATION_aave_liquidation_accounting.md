## 1. Confirmed Bugs in CSV Generation

The file `sim_tests/archive_tests/balanced_scenario_monte_carlo.py` generates `comprehensive_agent_comparison.csv`. Two CSV columns are broken for AAVE agents:

### 1a. `BTC_Amount` is hardcoded to 1.0

**Location:** `balanced_scenario_monte_carlo.py:2292`

```python
"BTC_Amount": 1.0,  # AAVE agents also have 1 BTC
```

This is hardcoded rather than read from the agent's actual post-liquidation state. The AAVE engine *does* correctly reduce `supplied_balances[Asset.BTC]` during liquidation (`aave_agent.py:211`), but the CSV ignores this.

The AAVE results dict *does* contain `remaining_collateral` (from `get_detailed_portfolio_summary`, `aave_agent.py:284`), but the CSV generation doesn't use it.

**Impact:** Anyone reading the CSV sees 1.0 BTC for liquidated agents, which contradicts the `Cost_of_Liquidation` column showing ~$35k of collateral was seized.

**Verify:** Compare `remaining_collateral` in the JSON results (`comprehensive_ht_vs_aave_results.json`) against the hardcoded 1.0 in the CSV for the same agents. The JSON should show reduced BTC amounts for liquidated agents.

### 1b. `Collateral_Lost` is always $0 due to missing key

**Location:** `balanced_scenario_monte_carlo.py:2288`

```python
"Collateral_Lost": agent.get("total_liquidated_collateral", 0),
```

This reads `total_liquidated_collateral` from the AAVE outcome dict. But the outcome dict generated by `_generate_aave_results` (`aave_protocol_engine.py:365-379`) does NOT include a `total_liquidated_collateral` key. The key exists on the agent state object (`aave_agent.py:230`: `self.state.total_liquidated_collateral`), and it IS included in the `get_detailed_portfolio_summary` return value (`aave_agent.py:292`), but it is NOT propagated to the outcome dict.

**Impact:** `Collateral_Lost` is $0 for every AAVE agent in the CSV, including liquidated ones. This makes the column useless.

**Verify:** Confirm that `total_liquidated_collateral` is absent from the outcome dict keys. Then check whether `Collateral_Lost` was intended to track a different quantity than `Cost_of_Liquidation`, or whether they should be equal.

## 2. `Cost_of_Liquidation` Semantics

### What it measures

`calculate_cost_of_liquidation` (`aave_agent.py:243-257`) sums `btc_value_seized` across all liquidation events. This is the GROSS value of BTC collateral sold during liquidation. Its docstring says "This represents the actual cost to the agent from liquidations," which is misleading.

### Why it's not the agent's actual loss

During AAVE liquidation (`execute_aave_liquidation`, `aave_agent.py:158-241`):
1. 50% of debt is selected for repayment (`debt_reduction = current_debt * 0.50`)
2. BTC seized = `debt_reduction * 1.05 / btc_price` (debt + 5% penalty, in BTC)
3. Agent's BTC balance is reduced by `btc_to_seize`
4. Agent's MOET debt is reduced by `debt_reduction`

The agent loses `btc_to_seize * btc_price` of collateral but gains `debt_reduction` of debt relief. The net realized loss is only the 5% penalty: `debt_reduction * 0.05`. This matches `Liquidation_Penalties` in the CSV.

**Numerical check:** For every liquidated agent in the CSV, verify that `Liquidation_Penalties / Cost_of_Liquidation ≈ 0.0476` (which equals `0.05 / 1.05`). This was spot-checked and holds, but should be verified exhaustively.

### What it DOES represent

`Cost_of_Liquidation` is the total value of collateral that changed hands (gross forced sale). This is a meaningful metric (it represents position reduction), but it should not be called a "cost" or "loss" without qualification.

**Action:** The `calculate_cost_of_liquidation` docstring should be updated. Consider whether a separate `net_liquidation_loss` method (returning just the penalty) would be useful.

## 3. `Final_Net_Position` Consistency Check

`Final_Net_Position` in the CSV comes from `get_detailed_portfolio_summary` → `net_position_value` (`aave_agent.py:270-277`):

```python
net_position_value = btc_value + yt_value - debt_value
```

where `btc_amount = self.state.supplied_balances.get(Asset.BTC, 0.0)` (the ACTUAL post-liquidation amount).

This means `Final_Net_Position` correctly reflects the reduced BTC balance, but `BTC_Amount` in the same CSV row is hardcoded to 1.0. The two columns are inconsistent.

**Investigation tasks:**

a) For each liquidated AAVE agent, reconstruct `Final_Net_Position` from the JSON data:
   - Get `remaining_collateral` (actual BTC) × `final_btc_price` + `yield_token_value` - `current_moet_debt`
   - Verify this matches the CSV's `Final_Net_Position`

b) For each liquidated AAVE agent, verify that:
   - `initial_btc_amount` (1.0) minus `remaining_collateral` equals `btc_seized` from the liquidation event
   - `btc_seized * btc_price_at_liquidation` equals the `btc_value_seized` stored in the event
   - The event's `btc_value_seized` equals the `Cost_of_Liquidation` in the CSV (for single-liquidation agents)

c) For surviving AAVE agents: verify `BTC_Amount` truly is 1.0 (no spurious liquidations).

## 4. Liquidation Timing and Mechanics

### 4a. When exactly does liquidation trigger?

The engine calls `_check_aave_liquidations(minute)` at `aave_protocol_engine.py:171`, AFTER `_process_aave_agents(minute)` at line 168. This ordering means:
- Price updates → agent actions (YT purchases at minute 0) → liquidation check

**Question:** Is there a minute-0 edge case where agents buy yield tokens and then immediately face a liquidation check? At minute 0, BTC price hasn't declined yet, so this should be safe. But verify that `update_btc_price(0)` returns the initial price.

### 4b. Single vs. multiple liquidations per agent

The liquidation check runs every minute. If one liquidation (seizing 50% of debt) doesn't restore HF above 1.0, will the agent be liquidated again the next minute?

**Investigate:** In the JSON results, check `liquidation_events` per agent. The CSV shows `Liquidation_Events: 1.0` for all liquidated agents in the current results, suggesting single liquidation suffices. But verify:
- After a single liquidation, is the agent's HF always > 1.0?
- If not, is the agent liquidated again the next minute?
- This was a known issue pre-F4 fix (cascading liquidations, 3 per agent). Verify the F4 fix resolved this completely.

### 4c. Correctness of the 50% + 5% calculation

Trace through one specific liquidation event end-to-end with exact numbers:
- Pick a liquidated agent (e.g., Run 1, agent0, initial HF 1.2658)
- Determine: at what minute did HF ≤ 1.0?
- What was the BTC price at that minute?
- What was the MOET debt at that minute (including interest)?
- Compute: `debt_reduction = moet_debt * 0.50`
- Compute: `btc_value_needed = debt_reduction * 1.05`
- Compute: `btc_to_seize = btc_value_needed / btc_price_at_liquidation`
- Verify these against the stored liquidation event values in the JSON
- Verify: post-liquidation HF = `(remaining_btc * btc_price * 0.85) / remaining_debt`

## 5. Yield Token Handling for AAVE Agents

AAVE agents buy yield tokens at minute 0 (same as FCM) but never sell them (no rebalancing). After liquidation, the agent still holds YT.

**Questions:**
a) Does the YT value factor into the `net_position_value` computation? Looking at `aave_agent.py:275`: `yt_value = yield_summary.get("total_current_value", 0.0)` — yes, it does. But the CSV column `Current_Yield_Token_Value` is hardcoded to `0.0` at `balanced_scenario_monte_carlo.py:2294`. Is this a third CSV bug, or do AAVE agents genuinely have $0 YT?

b) If AAVE agents DO hold YT (they buy at minute 0), then `Current_Yield_Token_Value: 0.0` in the CSV is another hardcoded-zero bug, similar to 1a/1b.

c) If AAVE agents have non-zero YT value, this affects `Final_Net_Position` and all downstream comparisons. The YT value at the end of a 60-minute sim would be: `initial_yt_value * (1 + 0.10)^(60/525600) ≈ initial_yt_value * 1.0000114`. Negligible for a 60-minute sim, but still a data integrity concern.

d) Cross-check: In the JSON results, look at `yield_token_value` for AAVE agents. Is it truly zero, or is it the expected small value?
